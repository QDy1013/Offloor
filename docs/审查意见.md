# 「offloor」审查意见

2026-11-03 · 对象：`nopalou/` 全部代码、两份文档、交付报告

## 一句话结论

骨架是真的，能编译、能签名、自测能过，报告里也坦白了不少事。但有三类问题报告没说：

- **演示可能当场翻车。** 真机上回放的卡片很可能一张都出不来；手机转一下屏，卡片就全没了。
- **换成真实用户基本不能用。** "我是谁"在代码里写死成了虚构的李承宇。
- **几个关键数字是评测脚本写错了算出来的**，不是代码真有那么好。

下面每一条都实际跑过（复现方法见文末），没跑过的会单独注明"未验证"。

---

## 一、演示可能当场翻车（最优先）

### 1. 回放器发出 272 条通知，系统只放行前 50 条左右

`ReplayActivity.post()` 每条消息都用新编号发一条通知，而且从不清理。安卓系统规定，单个 App 同时挂着的通知最多 50 条，超过的直接丢弃（AOSP `NotificationManagerService` 里的 `MAX_PACKAGE_NOTIFICATIONS = 50`）。

演示脚本里能出卡的 5 条关键消息排在 **第 121、160、167、184、209 条**，全部在 50 条以后。所以真机上很可能一张卡都出不来。

> 未在真机验证（雷电没起来），但这是安卓的硬规则。修法很简单：每发一条就撤掉 20 条之前那条，让同时挂着的通知不超过 20 条。

### 2. 转屏或切深色模式，卡片全部消失

`MainActivity.onCreate()` 每次都 `new Engine(...)`，然后覆盖 `EngineHolder.engine`。转屏、切深色模式、改字体大小都会让界面重建，于是新建一个空引擎，旧卡片全部丢掉。

同类问题还有两个：

- **重启手机后通知全丢。** 系统会先拉起通知监听服务，这时界面还没打开、引擎还是 `null`，`NotifListener` 会把来的通知全部丢掉，直到你点开 App 为止。
- **没有任何存储。** App 被系统杀掉，所有待办就没了。

### 3. "读当前群"读到的是 offloor 自己的界面

按钮在 offloor 的主界面上，点下去的那一刻，当前窗口就是 offloor 自己，`getRootInActiveWindow()` 拿到的也是它自己。结果是把自己的按钮文字和卡片标题当成群消息又喂回引擎，根本读不到微信。

这条的后果比看上去严重：用户最想免于翻阅消息的大群通常开了免打扰，免打扰群**不发通知**。方案书里给这些群兜底的就是读屏，现在读屏读不到，**这些群实际上没有任何数据来源**。

## 二、换成真实用户就不灵

### 4. "我是谁"写死成了虚构人物

`Engine.java` 第 43–47 行把姓名"李承宇"、学号 20230137、"第3组"、"计科2301"、选修课都写成了常量，也没有设置界面。别人装上以后：

| 现象 | 原因 |
|---|---|
| 每个接龙都提示"你还没接" | 名单里永远找不到"李承宇" |
| @你 永远识别不出来 | 只认"李承宇/承宇/小李/李同学" |
| **名字里带"课"的群，老师布置的作业全部被吞掉** | 第 574 行：群名含"课"又不在写死的选修课列表里，就当作"与我无关" |

探针结果：在"高等数学课程群"里，张老师发"@所有人 周五 18 点前交第三章作业到学习通"，**出卡 0 张**。课程群是这个产品最核心的场景。

报告里写的"个人档案 ✅"，实际是写死的演示数据。

### 5. 任何人说一句"取消"，本群最新的卡片就被删掉

撤销的判断方式是：只要消息里出现"取消 / 忽略 / 作废 / 改成 / 改为…"，就去删或改本群**最新的一张卡**，不看是谁说的，也不看说的是什么事。

- 探针：老师发了交实验报告的通知，随后同学说"我把今晚的外卖取消了"，**作业卡被删了**。
- 留出集里，"这周实验课取消"这一句就**误删了 5 张卡**，其中有真待办（选课意向表、课后习题）。

### 6. 接龙：重复出卡、接了也不消、作业清单被当成接龙

| 场景 | 实际结果 |
|---|---|
| 微信接龙每有一个人接，整条就重发一次 | 3 个人接 → **出 3 张一模一样的卡** |
| 自己也接上了 | 前面 3 张"你还没接"**一张都不消失** |
| 老师发"本周作业：1. 完成习题 3.1 2. 预习第四章 3. 周五 18 点前提交" | 变成「**接龙：本周作业：（你还没接）**」，"3 人已接"，截止日期是 **3 月 1 日**（"习题 3.1"被读成了 3 月 1 日） |

带编号的作业清单在老师的通知里非常常见。

> 未验证：微信通知的正文里是否保留换行。如果不保留，靠"编号行"识别接龙和数人数的逻辑就全部失效。

### 7. 时间解析：常见说法有一半解析错

发送时刻设为 2026-12-20（周日）10:00：

| 原话 | 正确答案 | Python 版 | APK 里的 Java 版 |
|---|---|---|---|
| 明晚八点前交 | 12-21 20:00 | ✅ 20:00 | ❌ **23:59**（不认中文数字钟点） |
| 周五晚上8点30分前 | 12-25 20:30 | ✅ 20:30 | ❌ 20:00（分钟丢了） |
| 明天下午3点半前 | 12-21 15:30 | ❌ 15:00 | ❌ 15:00 |
| 1月10日前交（12 月发的） | 2027-01-10 | ✅ | ❌ **2026-01-10，已经过去了** |
| 作业要求2-3页，周五前交 | 12-25 23:59 | ❌ 2 月 3 日 | ❌ 2 月 3 日 |
| 明早8点交，晚了不收 | 12-21 08:00 | ❌ 20:00 | ❌ 20:00 |

评测为什么没发现：合成数据的 1729 条待办消息里，**中文数字钟点 0 条，"点半" 0 条**，全部是"8 点""18:00"这种阿拉伯数字写法。期末季"12 月说 1 月某日交"也是高频场景。

### 8. 通知正文拆"发送者"的逻辑有错

`NotifListener.java` 第 37 行取的是**两种冒号中靠后的那个**：

- 「王老师：周五18:00前交实验报告」被拆成发送者「王老师：周五18」，正文「00前交实验报告」，时间丢了。
- 微信格式「[3条]王老师: …」里的"[3条]"没有去掉。
- 不按 App 过滤，手机上所有 App 的通知都会进引擎（下载进度、验证码、音乐播放器……）。

演示脚本恰好一条都没触发，所以自测发现不了。

## 三、报告里的数字站不住

打个比方：**留出集**相当于期末考，**手写集**相当于老师临时出的附加题。

### 9. 手写集"23/23、23/23"：答案提前写在了卷子上

`run_hardset.py` 第 39 行：

```python
"sender": "王老师" if c["label"] in ("action", "notice") else "陈嘉禾",
```

发送者是**按标准答案**设置的：该出待办的，发送者一律设成"王老师"；不该出的，一律设成学生。而第一级规则恰好会把"老师说的 + 有动作词"判成待办。等于考卷上提前标好了"这题选 A"。

把这个泄漏去掉，同样 23 条待办题加上干扰题：

| 发送者设定 | 召回（该提醒的提醒到了几成） | 精确（提醒的里面真该提醒的占几成） |
|---|---|---|
| 原脚本（按答案设） | 23/23 = 100% | 23/23 = 100% |
| 全部设成老师 | 100% | **23/26 = 88.5%** |
| 全部设成学生 | **17/23 = 73.9%** | 100% |

报告只承认了"手写集用来调过参"，这个泄漏没有提到。

### 10. 留出集不是"没见过的题"，是原题重考

- 留出集里的非噪声消息，**82.3%（1876/2279）在训练集里一字不差地出现过**。按类别看：通知 184/188，讨论 536/536，闲聊 1049/1049，待办 107/506。
- 整个数据集 26951 条消息，**只有 1565 种不同的句子**。

所以 94.7% 衡量的是"背题背得怎么样"。报告说"合成数据模板化"是对的，但"按时间切分、从不参与训练"这个说法会让人以为题目是新的，实际不是。

### 11. 时间准确率 90.9%：错的其实是对的，对的是循环论证

- 被判成"时间错"的 28 张卡，**全部是被老师"更正"后正确更新了时间的卡**。评测拿更正前的旧答案去比，于是把对的判成了错。除此之外的错误是 **0 张**。
- 剩下的"100% 正确"是循环论证：数据生成器和解析器用的是同一套约定（"上课前"算早 8 点，"周末"算周日 23:59）。所以连关键词基线的时间准确率都是 100%。

### 12. 消融"去掉回复潮"根本没关掉回复潮

`run_eval.py` 传入 `use_burst=False` 后，`pipeline.py` 只是把 `stats` 换成了 `None`，实际关掉的是**"发送者常发通知"这个特征**。真正的回复潮逻辑 `_track_ack` / `_promote` 照常运行。另外，全量流水线在 8086 条消息里，回复潮总共只触发了 **1 次**。

README 里说"不是机制写错了，是数据的问题"，实际是**实验开关写错了**。

### 13. 报告的数字测的是 Python 版，APK 里跑的是另一份代码

Java 引擎是照着 Python 手工重写的一份，两边从来没有做过对齐测试，已经出现分歧：

- **时间解析**：第 7 条表格里一半的说法两边结果不同。
- **通知类消息**：Python 会出信息卡，Java 直接丢掉、用户什么也看不到。检查记录第 4 条说的修复只修了 Python 这边。
- **回复潮**：Python 按群统计，Java 不分群，A 群的"收到"会算到 B 群的消息头上。
- **接龙截止时间**：Python 取"截止"附近那一段，Java 取整条消息。

文档里写的"两端同口径"不成立。19 项 Java 断言只覆盖演示脚本这一条路径，而且绕开了通知监听、回放器和界面，这三处恰好是第一节那些问题所在的地方。

## 四、小问题

- **卡片标题没有任何指标在测，而评委第一眼看到的就是标题。** 演示卡"@李承宇 展示 PPT 你来做哈，周…"其实是原文截断；探针里出现过"@所有人  交实验报告到"；留出集里大量出现"前填选课意向表""前完成课后习题第 3 章（"这样的残片。
- **"没申请网络权限 = 消息不出手机"有漏洞。** "加入日历"会把群消息原文写进日历的描述栏，系统日历如果开了云同步，原文就上传了。
- **"找不到就不猜"没做到。** 待确认的卡点"加入日历"，会被塞进一个"明天此刻"的假时间；"上课前"一律当成早 8 点，也是猜的。
- **过期卡永远排在最上面，也没有"已完成"按钮**（`Card.done` 字段从来没用过）。
- **检查记录第 3、4 条写的修前修后数字完全一样**（78.8% → 86.7%），至少有一条是抄过去的。

## 建议的修复顺序

1. **演示能跑**：回放器撤旧通知；引擎只建一次，放进 Application 或 Service；卡片落盘（存成一个 JSON 文件就够）；通知监听里引擎为空时自己初始化。
2. **真机验一遍**：雷电不行的话，拿一台安卓手机开 USB 调试最快。
3. **档案可设置**：首次启动让用户填姓名、学号、班级、课程，去掉写死的常量。
4. **撤销收紧**：只认老师或班长发的、并且明确指向上一条通知的撤销（同一个人、30 分钟内、句子里有"上条/刚才/之前那个"）。
5. **接龙去重**：同群同标题只保留一张卡，自己接了就消掉；"编号行"识别改成必须带 #接龙，或者同时要求每行都像人名。
6. **时间解析**：补上中文数字、"点半"、"X分"、跨年，"2-3页"这种区间数字不当日期；Python 和 Java 用同一份测试用例对跑。
7. **评测修正**：手写集去掉按答案设发送者；时间准确率改用"更正后的答案"比；消融开关真正关掉 `_track_ack`；留出集按"句式模板"切分，不按时间切分。

## 怎么复现这些数字

脚本在 `docs/audit/`，不改动项目里的任何文件。

```bash
# Python：手写集泄漏、留出集重复率、误撤销、时间错误构成、合成数据时间写法
python -X utf8 docs/audit/probe_py.py .

# Java：直接驱动 APK 里的 Engine 跑真实场景
javac -encoding UTF-8 -d build/audit android/app/src/com/nopalou/Engine.java docs/audit/Probe.java
java -cp build/audit com.nopalou.Probe android/app/assets
```

## 名词小词典

| 词 | 大白话 |
|---|---|
| 召回 | 真该提醒你的事里，提醒到了几成。低了就是漏事。 |
| 精确 | 提醒你的事里，真该提醒的占几成。低了就是瞎报。 |
| 留出集 | 训练时藏起来、最后才拿出来考的题，相当于期末考。 |
| 标签泄漏 | 答案以某种方式混进了题目里，分数虚高。 |
| 消融实验 | 把某个零件拆掉再测一次，看它到底有没有用。开关没真关上，实验就白做了。 |
| 通知监听 | 手机允许某个 App 读取别的 App 弹出来的通知内容。 |
| 无障碍读屏 | 本来是给视障用户读屏幕用的系统功能，可以拿到当前界面上的文字。 |
| Activity 重建 | 安卓在转屏等情况下会把界面拆掉重搭，界面里新建的东西都会重新来一遍。 |
