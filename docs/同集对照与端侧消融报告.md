# Offloor「楼外」同集对照与端侧小模型消融评测报告

> 评测日期：2026-11-19｜代码基线：`v0.85`｜复现入口：[eval/run_llm_comparison.py](../eval/run_llm_comparison.py) + [eval/JavaAiEval.java](../eval/JavaAiEval.java)｜原始结果：[eval/llm_comparison_report.json](../eval/llm_comparison_report.json)

## 1. 实验目标与口径说明

为直接回答评审最关心的三个问题：
1. **为什么不直接把群消息全扔给大模型处理？**（对比「纯大模型全量直抽」vs「Offloor 本机三级引擎」vs「本机三级 + 大模型协同复核」）
2. **APK 内置的 GBNF 语法约束（`LocalLlmCore.judgeGrammar`）到底有多大用？**（对比有/无 GBNF 时的结构化有效输出率）
3. **1.5B 端侧小模型与更大参数模型在真实复核中的收益与边界分别是什么？**

### 统一实验设置（严格同集、同尺、零泄露）
- **冻结测试集**：[eval/strict_ood.jsonl](../eval/strict_ood.jsonl)（100 条全新人工构造现实风格消息，不以标签反推发送者）：
  - `50` 条非接龙待办/考试（其中 `40` 条明确截止时间，`10` 条故意使用「近期 / 这几天 / 有空时 / 等通知」等含糊表达，期望保持待确认不编造日期）；
  - `10` 条群接龙（`5` 条未接龙应提醒 + `5` 条本人已接龙不应提醒）；
  - `40` 条高混淆负例（老师/同学提问、第一人称自述、停课/调课/成绩发布/考试范围等纯告知、闲聊）。
- **核心代码真实复用**：[JavaAiEval.java](../eval/JavaAiEval.java) 直接在 JVM 上编译运行 APK 生产源码 `Engine.java`、`AiClient.java`、`LocalLlmCore.java`、`StudyPlanner.java`（含原版 `JUDGE_SYSTEM`、`buildJudgeRequest`、`judgeGrammar`、`stripThink`、`parseVerdicts` 时间防幻觉护栏与 `Engine.applyAi` 写回逻辑），**无任何手工改写或模拟**。
- **对比模型与推理环境**：
  - **端侧同款 1.5B**：`Qwen2.5-1.5B-Instruct (Q4_K_M)`（`1,065.6 MB`，与 APK `LocalLlmCore.RECOMMENDED_URL` 指向同一 ModelScope 权重）；
  - **较大参考模型 8B**：`Qwen3-8B (Q4_K_M)`（`4,983.3 MB`，关闭思考段 `--reasoning off` + `/no_think`，用于对照较大规模本地/近云模型）；
  - **推理引擎**：`llama.cpp`（`llama-server` b12541 Vulkan，本机 RTX 5070 Laptop 8 GB，`temperature = 0.0` 贪心解码，与 APK `offloor_llm.cpp` 采样方式一致；每批 3 条与 `LocalLlmCore.BATCH` 一致）。
- **直抽组公平性说明**：纯大模型直抽组（100 条分 34 批全量送入模型）将系统提示首句调整为“请直接判断下面每一条群聊消息”且不泄露本机 `local_guess`；对 10 条接龙消息，凡模型判 `todo=true` 均计入触发集合以检验其能否区分“未接/已接”。

## 3. 核心结论（用数字证明架构设计）

### 结论一：纯大模型全量直抽存在三大硬伤，Offloor 架构全面胜出
1. **相对时间换算极易出错**：即使是 5.23 GB 的 `Qwen3-8B`，在「本周五」「下周三」「明晚八点半」等中文相对日期换算上的准确率也只有 **42.5%（17/40）**（例如将 10 月 14 日周三发出的“本周五前”算成 10 月 21 日，将“明晚八点半”写成 `20:59`），1.5B 全量直抽更是只有 **27.5%（11/40）**；而 Offloor 本机确定性时间引擎达到 **90.0%（36/40）**，接入 8B 协同后达到全场最高 **92.5%（37/40）**。
2. **含糊时间严重编造幻觉，而本机证据护栏锁死 100% 克制**：面对 10 条“近期 / 这几天 / 有空时 / 等通知”消息，纯 1.5B 直抽 **10/10 全部编造具体截止时间并自标确定（克制率 0%）**，纯 8B 也有 **5/10 编造前文中的考试日期（克制率 50%）**。在 Offloor 混合模式下，由于 `AiClient.parseVerdicts` 强制核验时间与本机解析或原文逐字片段 `deadline_evidence` 一致，**无论接入 1.5B 还是 8B，含糊时间克制率均稳守 100.0%（10/10）**。
3. **接龙状态判别与算力成本碾压**：纯 1.5B 与纯 8B 直抽的接龙精确率仅 **50.0% / 62.5%**（无法可靠区分「名单里已有李承宇」），而本机状态机稳定达到 **100% / 100%**；更重要的是，前置三级筛选将大模型调用条数从 100 条压至 19 条，**总 Token 直降 79.6%～79.9%**（`39,581 → 8,056` / `42,018 → 8,462`）。

### 结论二：GBNF 语法约束是 1.5B 端侧小模型能否可用的决定性工程组件

在同一组真实升级队列（`19` 条消息，按 `BATCH = 3` 分 `7` 批）上对比关闭/开启 `LocalLlmCore.judgeGrammar(n)`：

| 模型与配置 | JSON 语法可解析批数 | `AiClient.parseVerdicts` 有效解析条目 | 有效条目率 | 实际写回 Engine |
|---|---:|---:|---:|---:|
| `Qwen2.5-1.5B` **无 GBNF**（仅靠 Prompt） | 7 / 7 | **1 / 19** | **5.3%** | 1 |
| `Qwen2.5-1.5B` **开启 GBNF** | 7 / 7 | **19 / 19** | **100.0%** | 15 |
| `Qwen3-8B` **无 GBNF**（仅靠 Prompt） | 7 / 7 | 16 / 19 | 84.2% | 9 |
| `Qwen3-8B` **开启 GBNF** | 7 / 7 | **19 / 19** | **100.0%** | 12 |

**根因定位**：关闭 GBNF 后，1.5B 小模型在几乎每一批都把外层对象 `{"items":[...]}` 丢掉，直接用 Markdown 代码块裸输出顶层数组 ```` ```json [ { ... }, ... ] ````；即使 8B 模型在第 2 批也同样发生了裸吐数组导致整批 3 条失效。`LocalLlmCore.judgeGrammar(n)` 在采样阶段用有限状态语法强制锁死 `{"items":[item1,...,itemN]}` 与合法日期格式，将 1.5B 的结构化可用率从 **5.3% 一步拉升至 100.0%（+94.7 个百分点）**。

## 4. 诚实复盘：1.5B 与 8B 复核的真实收益与短板

对触发升级的 19 条样本逐条核查前后变化（含 1 条本机漏报正例、12 条含糊/低置信已有卡、6 条边界负例）：

1. **真实召回与时间增益**：
   - 本机因非老师发送且未带 `@` 漏掉的学生口语点名待办 `ood_028`（`组长-林晓：承宇记得今晚 21:30 前把数据库接口文档发群里`），进入 `low_conf` 复核后，**1.5B 与 8B 均成功将其召回**（召回率 `94.0% → 96.0%`）；
   - **8B 进一步准确补全其截止时间 `2026-10-14 21:30`**，将端到端时间准确率推至全场最高 **92.5%（37/40）**；1.5B 虽然召回成功，但将截止时间与上下文串联，被时间护栏安全拦截后保持「待确认」，未写入错误时间。
2. **暴露出的 1.5B 真实短板（迎合偏差 / Sycophancy）**：
   - 在 5 条本机未出卡但送入复核的负例（`ood_076` 个人吐槽、`ood_083` 成绩已发布、`ood_084` 上机自带电脑、`ood_089` 考试范围通知、`ood_093` 闲聊「哈哈哈交了个寂寞」）上：
     - **8B 成功拒掉了 3/5 条**（`ood_076`、`ood_083`、`ood_093`），仅对边界最模糊的「自带电脑」「考试范围」补建了 2 张卡，整体精确率维持在 **94.1%**（F1 **95.0%**）；
     - **1.5B 将全部 19/19 条升级消息一律判为 `todo=true, confidence=0.9`**，导致上述 5 条负例全部误建卡片，精确率由 `97.9%` 降至 **88.9%**（F1 `92.3%`）。
3. **对产品与后续迭代的直接指导意义**：
   - 实测印证了 Offloor **「默认关闭 AI、本机三级引擎优先」** 的合理性（纯本机已达 95.9% F1 且 0 误杀）；
   - 对 1.5B 端侧模式，后续版本可引入**非对称权限策略**：默认优先让 1.5B 负责「已有待确认卡片的标题/地点/提交渠道整理」，对「未出卡消息凭空新建待办」提高置信门槛或交由云端/更大模型承担，从机制上根治小模型的迎合误报。

## 5. 一键复现命令与诚实边界

```bash
python eval/run_llm_comparison.py \
  --android-jar <Android SDK platforms/android-34/android.jar> \
  --json-jar <org.json.jar> \
  --llama-server <llama-server 可执行文件路径> \
  --small-gguf <qwen2.5-1.5b-instruct-q4_k_m.gguf> \
  --large-gguf <qwen3-8b.gguf> \
  --cache-dir <临时缓存目录> \
  --out eval/llm_comparison_report.json
```

**当前仍存在的评测边界（材料中如实声明）**：
- `strict_ood.jsonl` 仍为 100 条人工构造现实风格无泄漏基准，尚未替换为脱敏后的真实大学班级群聊连续采样集；
- 上述 1.5B/8B 质量对照在桌面端 `llama.cpp`（与 APK 同量化权重、同 GBNF 语法、同贪心解码）完成；真机推理耗时以 vivo V2505A 实测单次 `2.927s`（冷）/ `2.357s`（温）为参考，中低端机型分机型速度、连续多批后台耗电以及商用云端大模型（如 DeepSeek / Qwen-Plus）同集对比仍待后续补充。
